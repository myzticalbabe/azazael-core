# Resurrection, not piracy: the right-to-repair case, engineered on the 2600 (2026-11-01)

Recorded at the user's instruction: *"it is similar to the Right-to-Repair — they own the old
games they purchased and want to resurrect them on the Bleeding-Edge. Engineer flaming sword to
do this, the old Atari games etc."*

Track H is in [`tasks.json`](tasks.json) (`M-31` … `M-37`). **One of those tasks is already
code**: [`../../tools/sword_2600.py`](../../tools/sword_2600.py) inspects an owner's cartridge
and emits the conversion report the rest of the pipeline consumes. That is deliberate — a track
that begins with a working intake is a track, not a wish.

## 1. The framing that makes this the same argument as repair

Right-to-repair says: *you bought it, the maker stopped supporting it, you should be able to keep
it working.* Repair law was written for tractors and phones, and it works by granting access to
**the thing you own** — not by handing you someone else's design.

The gaming equivalent fails at a different point. You still own the cartridge; what died is the
**machine**. So the repair is a software one: implement the machine, keep the cartridge. That is
exactly the shape US law has already blessed:

| precedent | holding | date | tier |
| --- | --- | --- | --- |
| **Sega v. Accolade** | reverse engineering for compatibility is fair use | 1992 | A |
| **Sony v. Connectix** (9th Cir.) | building an emulator by reverse engineering is **fair use**; intermediate copying during the process included | 2000 | A |
| DMCA §1201 triennial | a new **game preservation** exemption was **refused**; renewed exemptions run Oct 2027 – Oct 2030 | 2024-10-25 | A |
| *Stop Destroying Videogames* ECI | 1,294,188 verified signatures; Commission declined to propose legislation | 2026-01-26 | A |

Read together: **implementing the hardware is protected; unlocking the game is not.** So the
sword never decrypts, never patches, never ships an image. It reads the cartridge the owner
already has, and produces a *new* thing: a simulation plus a hash lock.

That single rule removes the entire DMCA §1201 category of risk — the category that killed the
2024 exemption request and that Yuzu settled over — and leaves only copyright in the game's
expression, which is why the shard carries no bytes of it.

## 2. Why the Atari 2600 is the best first case, in numbers

| fact | value | why it matters for conversion |
| --- | --- | --- |
| CPU | 6507 @ **1.19 MHz**, a 6502 with fewer pins | one instruction set to implement, fully documented |
| frame | **76 cycles/line × 262 lines** (NTSC) | ≈ 19,912 cycles per frame; the whole game budget is 50 microseconds per line |
| line | **228 colour clocks**, **3 colour clocks per CPU cycle** | the CPU/beam ratio is exact, so timing is arithmetic, not guesswork |
| RAM | **128 bytes** | the entire game state fits in a hash; no heap, no allocator, no pointer soup |
| display | **160×192**, raced — no framebuffer | the "renderer" is a *program*: register writes per scanline |
| arithmetic | integer only, no clock, no OS | **every 2600 game is already a deterministic frame-locked simulation** |

That last row is the whole thesis. A modern shard needs an exact integer sim and a separate
presentation layer; a 2600 game *is* an exact integer sim with its presentation interleaved into
the same code. Conversion is not translation into a foreign model — it is **separating two things
the hardware forced together**.

## 3. The insight that makes presentation convertible

On the 2600 the program writes `GRP0`, `PF1`, `COLUP0`… *while the beam is drawing*. There is no
image to copy and no artist file to extract. So the presentation is captured as a **raster
recipe**: for each scanline, which registers were written and when. That recipe is:

- small (a few hundred writes per frame, not a megabyte of texture);
- **tierable** — a handheld drops sprite resolution and palette depth, a desktop renders the same
  scanline program with a CRT shader; the ladder in
  [`reference-shards/highend_ladder`](reference-shards/highend_ladder) is the existing gate;
- and legally clean, because it describes *behaviour* (what the program did to the beam), not
  *expression* (the pixels it produced).

## 4. What is built, right now

`tools/sword_2600.py --inspect <rom>` — and it does none of the illegal things:

Real output, from a 4 KB synthetic fixture (`SEI / CLD / LDX #$FF / TXS / LDA #$00 / STA $0202 /
STA $80 / JMP` with RESET at `$F000`), captured on the 3.15t interpreter:

```
== .tmp_sword_fixture.a26
   size      4096 bytes -- 4K (no banking), 1 bank(s)
   sha256    c7ad0290aa22af388764df307b52d22af71496f29d2e63e80817677f2c9b573d
   reset     0xf000   irq 0xf000   nmi 0x0000 (the 6507 has no NMI/IRQ pin; the vectors
             exist in ROM regardless)
   code      8 instructions, 15 bytes code / 4081 bytes data
   top       STA x2, SEI x1, CLD x1, LDX x1, TXS x1, LDA x1
   hardware  WSYNC 0, graphics 0, timer 0, collisions 0, input 0
   -> no display or input register reached from the entry point after 8 instructions; the
      mapping or the entry is probably wrong, and the report should be treated as
      uninformative rather than as 'simple'
   class     R1 (the tool reads the owner's cartridge and ships no game bytes; the shard
             carries the reimplemented rules and a hash lock to the owner's own image)
```

That warning is the report's most important line, and it fired on the fixture that was meant to
look simple: `$0202` is `VSYNC`, not a graphics register, so a naive reading would have said
"this game draws nothing" when the truth is "this scan proved nothing". A tool that cannot tell
those apart is worse than no tool, because the second sentence is a claim about the game.

What it actually does:

1. **Intake** — accepts only known cartridge sizes (2K/4K/8K/16K/32K/64K) and refuses anything
   else *rather than guessing a mapping*. 2K maps at `$F800`, larger carts at `$F000`.
2. **Identity** — sha256 of the owner's file; this becomes the asset lock, so the shard cannot be
   given away with the game inside it.
3. **6502 decode** — the documented opcode set, derived from compact mnemonic groups so the table
   cannot drift from the instruction it names. Undocumented/illegal opcodes are **counted and
   stopped on**, never invented.
4. **Recursive scan** — from the RESET vector, following branches, `JMP` and `JSR`. A byte is
   called code only because control flow **reached** it; everything else is reported as data.
   (Most 2600 ROMs interleave jump tables with routines, so this distinction is the difference
   between a report and a lie.)
5. **Hardware profile** — reads and writes classified as TIA / RIOT / RAM / ROM, with counts for
   `WSYNC`, `VSYNC`, graphics registers, RIOT timers, collision registers and controller reads,
   then **advice** phrased as what the conversion must do: a beam-raced display becomes a raster
   recipe, a timer-driven frame means the tick length must match the reload, collision-register
   reads mean the shard must reproduce the hardware's *tolerance* instead of inventing hitboxes.
6. **No output path.** The tool prints a report; it has no `--out` for a modified image, no
   assembler, no patcher. That is a property, not an oversight: this file cannot be used to
   redistribute a cartridge.

Verified 2026-11-01 after M-32 landed: `--selftest` prints **`SELFTEST OK (27 decode controls, 11
scan controls, 15 mapper controls)`**, including the negative controls that matter — a RESET vector

## 5. Banking: the stage where a wrong answer looks like a good report

`M-32` is built (2026-11-01), and it is the interesting one because **a size cannot identify a
scheme**: an 8 KB cartridge can be F8, FE or 3F. Inferring the scheme from the size is how a
converter produces a confident wrong game, so the scheme is **measured** — every candidate is
run and the one that actually saw a switch access is reported, with its evidence:

```
== .tmp_f8.a26
   size      8192 bytes -- 8K (2 x 4K candidate banks), 2 bank(s)
   mapper    F8 x2 of 4096 bytes in 0xf000-0xffff -- 2 x 4K; any access to $1FF8/$1FF9 is
             the switch, read or written; entry bank 1 (source: measured, 1 switch accesses)
   banks     2 of 2 reached
             bank 0               3 instr      7 B code /  4089 B data
             bank 1  entry        3 instr      7 B code /  4089 B data
   switch    bank 1 -> bank 0 at 0xf004 via 0x1ff8, resume 0xf007
   => every bank was reached, so the switch map is complete for F8
```

Three properties make that trustworthy rather than merely plausible:

- **the worklist is (bank, offset), not an address.** The same address is different code
depending on the selected bank. A switch resumes at the instruction *after* the switching
access, in the **new** bank — which is what the hardware does, and the reason a one-bank scan
cannot see the rest.
- **power-on selects the LAST bank.** The vectors at the end of the file always belong to the
entry bank, so bank 0 is usually the *unreached* one, not the first one.
- **an unreached bank is never reported as empty.** Forced F8 on a cartridge that switches at
`$1FF0` (an address no modelled scheme uses) gives: `1 of 2 reached`, `bank 0 0 instr NOT
REACHED`, and the verdict line *"the bytes there are reported as data because nothing reached
them, not because they are empty"* — with the entry bank still fully decoded, so the report is
not a zero-code image that reads as an empty game.

Modelled: **F8, F6, F4, FE, 3F**. Refused by name, never approximated: **E0, E7, F6SC, F4SC, 3E,
DPC**, and any 64 KB image — because no modelled scheme covers it and treating it as one window
would decode bank-switch accesses as ordinary stores. `3F` selects a bank by the *value* written to
`$003F`, so a value the scan cannot resolve to an immediate is reported `UNRESOLVED` rather than
assumed to be bank 0.

Verified: `--selftest` prints **27 decode, 11 scan, 15 mapper** controls; `tests/test_sword_2600.py`
gives **13 passed**.

## 6. What is *not* built (and the tasks that would build it)

| id | stage | why it is hard |
| --- | --- | --- |
| **M-33** | raster-kernel capture | the per-scanline register writes must be recorded *with cycle positions*, i.e. a real TIA model, not a static scan |
| **M-34** | integer sim extraction | RAM variables must be identified as position/velocity/score by evidence, not by guesswork |
| **M-35** | divergence lab | "feel" is measured: frame budget, input latency, collision tolerance — the gate is a divergence count, not an opinion |
| **M-36** | tier ladder + CRT presentation | reuses the ladder gate; the recipe must be *identical* across tiers with only resolution changing |
| **M-37** | audio recipe | `AUDC/AUDF/AUDV` are a 2-bit waveform machine; a patch table is extractable and honest, sampling the output is not |

`M-31` (intake) and `M-32` (banking) are `completed`, with their limits recorded rather than
hidden: documented opcodes only, six schemes modelled and six refused, no TIA model, and no claim
about the game's rules.

## 7. Bleeding edge, precisely

"Resurrect on the bleeding edge" is not a shader. Once the sim is extracted at its native frame
rate (NTSC 59.94), the rest of this tree's work applies directly. The orchestrator that makes the
claim testable is built, and it belongs to **Project FLAME** (the game engine project) rather than
to FLAMING SWORD (the code-fixing project): **`Project_FLAME/tools/flame_engine.py`** (M-38) is an
exact rational clock over 60000/1001 Hz with a frame pump that never loses a remainder, and
`--verify` prints a matrix rather than an assurance:

```
   rate   accel  ticks     frames    state              verdict
   60     1      599       600       0eef62ab4b962198   OK
   120    1      599       1200      0eef62ab4b962198   OK
   144    1      599       1440      0eef62ab4b962198   OK
   240    1      599       2400      0eef62ab4b962198   OK
   ...                                     (2x -> 1198, 8x -> 4795, same hash per row group)
   acceleration: 599 ticks reached in 600 frames at 1x, 2 in 300, 8 in 75
   control: 60 Hz-assuming clock at 60/240 fps -> ticks [599, 2397], 2 distinct hashes -> CAUGHT
   VERIFIED
```

What that establishes, and what it does not: **slicing invariance** (the same simulated time at
60 or 240 fps visits the same ticks and ends in the same state), **acceleration equivalence** (8x
is the same simulation reached sooner: 600 frames versus 75 for the same 599 ticks), and **no
tick skipped or served twice**. It does not establish that a game feels right — the machine it
drives is a stand-in with the 2600's constraints (integer only, bounded state), and the 2600 sim
plugs in at M-34 through the same four-method seam. The output says this in its own `scope`
field, because a VERIFIED line that implies more than it proved is the defect this whole track
is written against.

The control is the part worth trusting: a clock that assumes every display is 60 Hz is **right at
60 fps** and four times too fast at 240 — which is exactly why that bug ships in real games — and
the verifier catches it. An orchestrator that cannot be shown to fail is decoration.

It already found one real defect in itself: the first `run_to_ticks` stopped on frame boundaries,
so at 8x it overshot 299 ticks to 303 and compared two different instants. The fix was a
tick-exact comparison path — the same class of bug, one level up, that the engine exists to
prevent.

The rest of the tree's work applies directly:

- **exact sim at 60 Hz, presentation at 120/240** — the `dual-rate-sim` capability already in the
  catalogue: interpolation cannot desynchronise gameplay because gameplay is not presented;
- **rollback netcode for two-player carts** — the `mirrorcast` family: the state is 128 bytes and
  integer, which is the cheapest rollback payload in the entire catalogue;
- **verifiable score runs** — a transcript plus a state hash; the same trick that makes a golden
  run a golden run turns a high score from a screenshot into a proof;
- **tier 0 as the original's hardware class** — the ladder's lowest rung is what the game shipped
  for, and the honest claim is "tier 0 looks like 1979; tier 3 looks like 1979 with a good CRT";
- **a CRT shader as a recipe, not an asset** — scanline gate, phosphor decay and NTSC artefacting
  are parameters, which is what keeps the shard a few kilobytes.

## 8. Failure modes, stated before they bite

- **Illegal opcodes are real.** Some 2600 games use undocumented instructions for size. The tool
  stops and counts; a converter must implement the stable subset and *report* rather than assume.
- **Banks multiply the work, and the wrong scheme is invisible.** A 32K cart with 8 banks is 8
  scans plus a switch model. Measured 2026-11-01: the per-bank split, the switch list and the
  resume addresses all look equally plausible when the scheme is wrong — which is why the scheme
  is measured and `ambiguous` / `no switch found` / `NOT REACHED` are printed outcomes instead of
  a silent pick.
- **TIA quirks are the game.** `HMOVE` timing, `RESP` reset delays and the `WSYNC` race are where
  a naive reimplementation becomes "almost right", which for a 1979 audience is wrong.
- **PAL is not NTSC.** 50 Hz, 312 lines, different palette. The shard must declare which machine
  it models, or two players will disagree about speed.
- **This is per-game work, not a bulk converter.** A tool that claims to convert a library is
  claiming to have solved every one of the above at once. The honest product is: intake first,
  then one game, then the second game, then the build that makes the third cheap.

## 9. Why this is the strongest resurrection case in the whole problem

Of every discontinued game, the 2600 is the one where **the owner's copy is small enough to hash,
the machine is small enough to reimplement, the state is small enough to verify, and the law has
already said the emulator is fair use.** If shard resurrection cannot be made to work here, it
cannot be made to work anywhere — and if it works here, it produces the argument, the tooling and
the legal record that the harder cases (16-bit, DOS, dead MMOs) need.
