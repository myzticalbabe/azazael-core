# wasm cosine SIMD — what was wrong, and what the change actually bought

Board row `47009` said: *"Fix wasm-bindgen to export `cosine_similarity_simd`. Deliverable:
working SIMD export."* Two of the three premises were wrong, and the third defect was real
but different from the one named. All numbers below are from `node bench.mjs <pkg>`,
1536-dim `Float32Array` pairs, 20,000 timed calls after 2,000 warm-up calls, Node 24.14.0,
wasm-pack 0.15.1 / rustc 1.95.0.

## Premise check

| premise | measured |
|---|---|
| the export is missing | **wrong** — `cosine_similarity_simd` was in `lib.rs`, in `pkg/*.js`, in `pkg/*.d.ts`, and in the built binary |
| it needs wasm-bindgen attention | **wrong** — wasm-bindgen was exporting it correctly the whole time |
| the build enables SIMD | **wrong twice**: `Cargo.toml` declares `simd = []` (an empty feature enables nothing) and there was no `.cargo/config.toml`, so no `target-feature=+simd128` ever reached rustc |

## Why the name was a lie

`cosine_similarity_simd` and `cosine_similarity_wasm` were **the same scalar loop**, differing
only in an `i as u32` cast, and both were documented as "auto-vectorized by LLVM". Three
independent reasons no vectoriser could have helped:

1. no `simd128` target feature (fixed here);
2. the loop called `Float32Array::get_index` **per element** — a call into the JS heap, so
   ~97% of the time was not arithmetic at all. A memory-bound loop does not vectorise;
3. **FP addition is not associative.** LLVM will not vectorise `dot += a[i]*b[i]` even *with*
   `+simd128`, because reordering changes the result. SIMD here has to be written, not
   requested.

## Measured, separated so the claim can be attributed

| build | `cosine_similarity_simd` | `cosine_similarity_wasm` | wasm size |
|---|---|---|---|
| **before** (`pkg.baseline-2026-11-01/`) — per-element reads, scalar body | 16.688 us | 17.153 us | 15,219 B |
| **copy + scalar kernel**, `-simd128` (`pkg.nosimd/`) | 0.892 us | 15.666 us | 16,454 B |
| **copy + SIMD kernel**, `+simd128` (`pkg/`) | 0.523 us (0.385 on re-run) | 17.293 us | 16,930 B |

- **Removing the per-element JS-heap reads is most of the win**: 16.688 → 0.892 us, **~18.7×**.
  It came from copying each `Float32Array` once (`to_vec()`) and running a slice kernel.
- **The SIMD lanes are worth a further ~1.7–2.4×** (0.892 → 0.523; 0.914 → 0.385 on the second
  run): real, measured, and *smaller than the copy fix*. Anyone quoting one total should say
  which part it came from.
- Total, like-for-like on the same run: **16.688 → 0.523 us ≈ 32×**.
- `cosine_similarity_wasm` is deliberately **left as the old per-element path** so the
  comparison above stays honest — it is the control, not dead code.

## Numerics, because a faster wrong answer is worse

Against a JS f64 reference: SIMD build `max_dev = 4.3e-8`; scalar build `4.93e-7`. Lane order is
fixed (four partial accumulators, then a pairwise horizontal sum), so the result is deterministic
for a given input, and it is *closer* to the reference than the old scalar sum on this vector pair.
`bench.mjs` fails with exit 1 if `max_dev > 1e-5`, so this cannot silently rot.

## What a caller must know

The glue is `--target web`: the exported functions call through a `wasm` binding that is
`undefined` until init resolves. Importing and calling directly throws
`Cannot read properties of undefined (reading 'cosine_similarity_simd')` — which is exactly how
`bench.mjs` failed on its first run. Init with a compiled module to avoid the fetch path:

```js
const mod = await import("./pkg/azazael_wasm.js");
await mod.default(await WebAssembly.compile(await readFile("pkg/azazael_wasm_bg.wasm")));
```

## Left open, on purpose

- `[features] simd = []` in `Cargo.toml` is still a **no-op**. Functionality now comes from
  `.cargo/config.toml`, which cannot be toggled per build without `RUSTFLAGS`. Either delete the
  feature or make it `compile_error!` when off — do not leave a switch that switches nothing.
- `wasm-opt` runs on every `wasm-pack build`; the SIMD binary is 476 B larger than the
  non-SIMD one and still faster, so the optimisation is preserved — verified by running both
  builds through the same bench, not by reading the build log.
